## 1. 概述

### 1.1 项目背景

《计算机网络技术》实验与课程设计强调理论联系实际。TCP/IP 是 Internet 的核心，Socket 是操作系统向应用程序暴露的网络编程接口。本课题要求学生：

- 掌握 TCP 面向连接通信的基本过程；
- 设计并实现非平凡的应用层协议；
- 体现软件工程：分工、文档、可运行代码、测试；
- **必须引入大语言模型（LLM）** 作为辅助分析或智能组件。

据此，本组实现一套 **CN-Chat** 系统：C++17 POSIX Socket 多客户端聊天室，支持文件分块传输（客户端互传或上传服务器），并用 Python 调用 OpenAI 兼容 API（或离线 mock）对运行日志做协议/TCP 层面的诊断，供答辩讲解。

### 1.2 设计目标

| 编号 | 目标 | 度量 |
|------|------|------|
| G1 | 服务器稳定监听并服务多客户端 | ≥2 客户端同时在线互聊 |
| G2 | 自定义帧协议正确划分消息 | 粘包场景下解析不错乱 |
| G3 | 文件可上传服务器或中继到指定昵称 | 内容与源文件一致 |
| G4 | 客户端 CLI 可用 | `/nick /say /sendfile /quit` |
| G5 | LLM 诊断可演示 | 无密钥 mock 仍输出完整中文报告 |
| G6 | 文档支撑评分 | 原理、步骤、测试齐全 |

### 1.3 范围与非目标

**范围内**：局域网/本机 TCP；明文协议；线程并发；日志+LLM。  
**非目标**：TLS 加密、用户鉴权数据库、图形界面、跨公网 NAT 穿透、断点续传。

## 2. 相关网络原理

### 2.1 OSI / TCP-IP 模型中的位置

本系统主要工作在：

- **传输层**：TCP（面向连接、可靠、全双工字节流）；
- **应用层**：自定义 CN 帧协议（聊天、文件控制与数据、系统消息）。

IP 负责主机到主机的分组投递，TCP 在端口间提供进程到进程的可靠通道。应用不必处理重传与乱序，但必须处理**字节流没有消息边界**这一本质特性。

### 2.2 TCP 连接建立与释放

**三次握手（建立）**：

1. 客户端 `connect` → 发送 SYN；  
2. 服务器内核应答 SYN+ACK（此时 `listen` 队列中的连接可被 `accept`）；  
3. 客户端再发 ACK，连接进入 ESTABLISHED。

**四次挥手（释放）**：任一方 `close`/`shutdown` 触发 FIN，对端确认；半关闭允许另一方向继续发送，直至也关闭。

与本项目 API 映射：

| 动作 | 服务器 | 客户端 |
|------|--------|--------|
| 创建套接字 | `socket(AF_INET,SOCK_STREAM,0)` | 同左 |
| 绑定地址 | `bind(0.0.0.0:9000)` | 通常不主动 bind |
| 被动打开 | `listen` | — |
| 接受连接 | `accept` → 新 fd | — |
| 主动打开 | — | `connect` |
| 收发 | `recv`/`send` | 同左 |
| 关闭 | `close` | `close` |

### 2.3 端口、多路复用与并发

服务器在 **知名/约定端口 9000** 上监听。每个成功 `accept` 的连接由内核分配新的套接字描述符。多个客户端同时连接时：

- **thread-per-client**：每连接一线程阻塞 `recv`（本项目采用，实现直观）；  
- 亦可 `select`/`poll`/`epoll` 单线程多路复用（本服务器 accept 循环使用了 `select` 超时以便响应信号）。

共享的“昵称 → fd”表需 **互斥锁**，否则广播时迭代与增删并发会数据竞争。

### 2.4 字节序

网络协议约定**大端（网络字节序）**。多字节整数（本协议的 `length`）必须 `htonl` 发送、`ntohl` 接收，否则在小端主机（x86）上长度会错乱，导致后续帧全部失同步。

### 2.5 粘包与半包

TCP 保证有序可靠，但一次 `recv` 可能：

- 读到半个应用消息（半包）；  
- 读到多个应用消息（粘包）；  
- 或二者组合。

**对策**：应用层定义明确边界。本项目采用 **固定 8 字节头 + length 字段**：先 `recv_all(8)`，再 `recv_all(length)`。这是课程设计中应重点阐述的知识点。

### 2.6 应用层协议设计原则

1. **可扩展**：保留 `version` 字段；  
2. **可调试**：类型枚举清晰，日志打印类型名；  
3. **防滥用**：限制最大帧长；  
4. **控制与数据分离**：FILE_META/END 为控制，CHUNK 为数据。

```
                 +---------------------------+
                 |   llm/diagnose.py (丁)    |
                 |  读日志 → Prompt → LLM/mock|
                 +-------------^-------------+
                               | 日志文件
+----------+    TCP :9000    +-+-------------+    TCP     +----------+
| client A | <-------------> |    server     | <--------> | client B |
|  (乙)    |   CN 帧协议     |     (甲)      |            |  (乙)    |
+----------+                 | 广播/中继/上传|            +----------+
                             +---------------+
                                     |
                             server/uploads/
```

**模块划分**：

- `common/protocol.hpp`：帧编解码、`send_all`/`recv_all`（甲乙共用）；  
- `server/server.cpp`：连接管理、业务逻辑；  
- `client/client.cpp`：CLI 与收发线程；  
- `llm/`：诊断；  
- `docs/` + `protocol/`：丙维护的说明。

**数据流**：键盘输入 → 客户端组帧 → TCP → 服务器解析 → 业务（广播/写盘/转发）→ 组帧回写其他客户端 → 界面打印。

## 5. 应用层协议设计

详见 `protocol/PROTOCOL.md`。此处给出说明书级摘要。

### 5.1 帧布局

| 偏移 | 大小 | 字段 |
|------|------|------|
| 0 | 2 | magic = 'C''N' |
| 2 | 1 | version = 1 |
| 3 | 1 | type |
| 4 | 4 | length（uint32 大端） |
| 8 | length | payload |

### 5.2 主要类型与载荷

- **NICK**：纯昵称字符串。  
- **CHAT**：上行仅消息；下行 `发送者\\t消息`。  
- **FILE_META**：`filename\\tsize\\ttarget`（服务器补全 sender 后转发）。  
- **FILE_CHUNK**：原始字节，建议 32KiB/块。  
- **FILE_END**：结束信号。  
- **SYS / LIST / PING / PONG**：辅助。

### 5.3 状态机（文件）

发送方：`IDLE → (META) → SENDING_CHUNKS → (END) → IDLE`  
接收方/服务器：`IDLE → (META 打开文件或记录目标) → RECV_CHUNKS → (END 关闭) → IDLE`

异常：无 META 却收到 CHUNK → SYS 提示；目标昵称不在线 → 拒绝 META。

### 5.4 时序图（文字版）

**聊天：**

```
乙A                甲                 乙B
 |--NICK Alice---->|                   |
 |<--SYS 欢迎------|                   |
 |                 |--SYS 加入-------->|
 |--CHAT hi------->|                   |
 |                 |--CHAT Alice\\thi-->|
```

**上传 `*`：**

```
乙A --FILE_META(file,n,*)--> 甲 打开 uploads/Alice_file
乙A --FILE_CHUNK* ----------> 甲 写入
乙A --FILE_END -------------> 甲 关闭并 SYS 广播
```

## 6. 服务器详细设计（甲）

### 6.1 模块结构

- `main`：解析 `-p/-l`，创建监听套接字，循环 `select+accept`，为每个连接 `detach` 线程；  
- `handle_client`：循环 `recv_frame`，按 type 分发；  
- `broadcast`：对除发送者外所有 fd 发帧；  
- `g_clients`：`map<fd, {nick,addr}>`；  
- `g_xfers`：按发送方 fd 记录文件传输上下文。

### 6.2 关键算法：广播

1. 加锁复制 fd 列表（避免持锁调用可能阻塞的 `send`）；  
2. 解锁后逐个 `send_frame`；  
3. 失败仅记日志（完整实现可进一步踢掉连接）。

### 6.3 文件中继策略

- `target == "*"`：服务器本地 `ofstream` 写 `uploads/{sender}_{filename}`；  
- 否则：查找目标 nick 的 fd，原样转发 META/CHUNK/END。

### 6.4 日志

时间戳 + 事件（accept、nick set、CHAT、FILE_*、leave），供丁模块分析。

### 6.5 优雅退出

捕获 SIGINT/SIGTERM，`g_running=false`，accept 侧 `select` 1 秒超时醒来后关闭 listen fd。

## 7. 客户端详细设计（乙）

### 7.1 线程模型

- **接收线程**：阻塞 `recv_frame`，按类型刷新 UI（打印到 stdout）；  
- **主线程**：读 `stdin` 解析命令并 `send_frame`。

输出使用互斥锁，避免与 `> ` 提示符交错混乱。

### 7.2 命令映射

| 命令 | 帧 |
|------|-----|
| `/nick X` | NICK |
| `/say M` 或裸文本 | CHAT |
| `/list` | LIST |
| `/sendfile path [target]` | META+CHUNK*+END |
| `/ping` | PING |
| `/quit` | 关闭套接字 |

### 7.3 收文件

收到 FILE_META 后打开 `recv_{sender}_{filename}`，CHUNK 追加写入，END 关闭并提示完成。

## 8. LLM 诊断模块设计（丁）

### 8.1 动机

课程强制使用大模型。将 LLM 用于**运维/教学诊断**而非代替网络功能，既合规又有辨识度。

### 8.2 流程

1. 读取日志（过长则头尾截断）；  
2. 构造 System Prompt（角色=网络助教）+ User Prompt（嵌入协议摘要与日志）；  
3. 若存在 `OPENAI_API_KEY` 且未 `--mock`，POST 到 `{BASE_URL}/chat/completions`；  
4. 否则运行 **规则引擎 mock**：根据关键字（listening、accept、CHAT、FILE_*、fail…）生成结构化中文报告；  
5. API 失败时自动降级 mock，保证答辩不翻车。

### 8.3 环境变量

- `OPENAI_API_KEY`  
- `OPENAI_BASE_URL`（默认官方，可换兼容网关）  
- `OPENAI_MODEL`（默认 `gpt-4o-mini`）

仅依赖 Python3 标准库，无 pip 安装压力。

## 12. 总结与体会

本设计将 **TCP Socket 编程**、**应用层协议工程**与 **LLM 辅助分析**结合，满足课程对网络性、工程性、智能性与难度的要求。甲乙通过公共帧库并行开发，丙保证文档深度，丁负责智能诊断与答辩主线，四人职责清晰。

通过本项目，成员加深了对三次握手、字节流边界、字节序与并发同步的理解，并体验了“先协议后编码、先联调后优化”的软件过程。
